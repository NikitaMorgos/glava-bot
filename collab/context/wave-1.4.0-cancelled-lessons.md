# Волна 1.4.0 отменена — lessons learned

**Дата:** 2026-05-08
**Автор:** Опус
**Связанные:** [PR #14 закрыт без мержа](https://github.com/NikitaMorgos/glava-bot/pull/14), [task 033](../tasks/033-le-fact-preservation.md), [task 034](../tasks/034-le-ch01-timeline-preservation.md), [karakulina-versions-metrics.md](karakulina-versions-metrics.md)

---

## TL;DR

Волна 1.4.0 (PR #14) была спроектирована как защита от **«регрессии #7 — Stage 3 LE удалил эпизод про огурцы»**. При прямой проверке артефакта `book_FINAL_stage3_v53b.json` обнаружено что **огурцы в нём присутствуют** — регрессия не существует. PR #14 закрыт без мержа. Это потеря ~2 часов работы (код, промпт, тесты, task 033) на лечение фантомного класса.

---

## Что мы построили в волне 1.4.0

- `pipeline_utils.validate_le_fact_preservation` (~180 строк): после Stage 3 LE проверяет что каждое event из fact_map.timeline имеет ≥2 предметных маркеров (stem-substring match) в book_after_le.
- Helpers `_extract_event_markers`, `_marker_stem`, `_event_present_in_book` — переиспользование object markers test FC v2.13.
- LE v3 → v3.1 промпт с TOP-PRIORITY ЗАПРЕТОМ 0 «не удалять события timeline».
- `--allow-le-fact-loss` flag в `test_stage3.py`.
- 19 unit-тестов в `test_le_fact_preservation.py`, включая «v53b регрессионный».
- task 033 spec.

**Все тесты PASS (117 = 98 предыдущих + 19 новых).** Код качественный. Просто **закрывает несуществующий класс**.

## Как мы ошиблись

**Курсор отчитался по v53b:**
> «Сценарий C подтверждён. Stage 3 Literary Editor УДАЛИЛ эпизод. book_FINAL_stage3 — огурцов нет.»

**Никита и Опус приняли это как факт.** Не открыли `book_FINAL_stage3_v53b.json` сами. Опус спроектировал защиту, написал код, тесты, промпт, task 033 spec, открыл PR #14.

**При финальной проверке (после расширения задачи Никитой):**
- Опус попросил Курсора закинуть артефакты v53b в репо
- Курсор закинул в ветку `feat/v53-artifacts`
- Опус открыл `book_FINAL_stage3_v53b.json` через `git show feat/v53-artifacts:...`
- В ch_02: «...когда **Владимир привёз огурцы в хорошем чешском чемодане из Молдавии**...» — эпизод присутствует.

**Регрессии #7 не существует.** Курсор ошибся в диагностике v53b.

## Что мы нарушили — `dev-review-protocol.md`

Прямая цитата протокола, который сами же написали:

> **«Артефакт ≠ побочный эффект.** При любом «X сделано» — открыть сам артефакт, не верить proxy-метрикам типа «pytest passed», «exit 0», «PR merged». Зафиксировано в `collab/context/dev-review-protocol.md`.»

И второй пункт:

> **«Posture-forcing observation.** При закрытии задачи — обязательно одно предложение конкретного наблюдения о финальном артефакте: «открыл PDF v46, на стр 5 видно...». Не «PASS, файлы на местах».»

**Курсорская формулировка** «book_FINAL_stage3 — огурцов нет» была **proxy от него** (он сам открыл и сделал свой posture-forcing). Опус принял proxy как факт без своей независимой проверки.

Это ровно тот класс ошибки против которого был написан протокол. Защита была у нас в репо. Мы её не применили на самих себе.

---

## Корневая причина — ленивая верификация в распределённой команде

Курсор работает на сервере, видит свежие артефакты. Опус работает с репо, артефактов сразу не имеет. Между ними — пересказ через Никиту. Каждый шаг пересказа — потеря точности.

**Что должно было произойти:**

1. Курсор: «Сценарий C, диагноз прилагаю» → закидывает в ветку артефакты сразу
2. Опус: открывает артефакты → проводит **независимую** проверку → подтверждает или опровергает диагноз
3. Только после этого: проектирование защиты

**Что произошло:**

1. Курсор: пересказ + диагноз без артефактов в репо
2. Опус: принял диагноз → начал проектировать → попросил артефакты после написания PR
3. Артефакты пришли → проверка показала фантом → откат

**Стоимость ошибки:** 2 часа Опуса + время на ревью. Не катастрофа, но в системе с 9 PR мутирующих регрессий — это паттерн который можно и нужно сломать.

## Что меняется в процессе

**Новое правило для Опуса:**

> При получении диагностики Курсора с предложением «нужна новая защита X» — **первое действие** это **запрос артефактов в репо** (не в чате). Без артефактов — не проектируем защиту. Артефакты в чате как «вот тут видно...» — недостаточно.

**Новое правило для Курсора:**

> При диагностике с verdict «новый класс мутации» — **сразу** запушить артефакты в репо (отдельный PR с одной только runs/ папкой, не блокирует основной). Не ждать запроса от Опуса.

**Новое правило для Никиты:**

> Перед одобрением «давай делать волну X» — спросить «Опус, ты уже открыл артефакт сам?». Если ответ нет — сначала артефакт, потом одобрение.

Это **не процесс**, это **триггер**. Триггер на распределённую коллабу с LLM-агентами.

## Что сохраняется из волны 1.4.0

**Код можно полностью выкинуть** — он закрывает класс который не существует. Но:

- **`_marker_stem` helper** — полезный паттерн для русской морфологии без лемматизации. Если когда-нибудь понадобится stem-based substring search — есть готовая функция.
- **Object markers test scripted version** — концепт может пригодиться для других защит (например, generalization на других субъектах в волне 1.5.0).
- **19 тестов как ad-hoc framework** — структура тестов на event preservation хорошая, можно переиспользовать.

Поэтому код из PR #14 не удаляется насильственно — пусть лежит в ветке `claude/wave-1.4.0-le-fact-preservation` как reference. Основной `main` не трогается.

## Реальная регрессия найденная в той же диагностике

При прямой проверке артефактов обнаружено что **LE удаляет `chapters[ch_01].timeline`**. Stage 2 GW v2.16 на TR2 правильно генерирует 6 этапов жизни (1920-2005). Stage 3 LE возвращает главу без поля `timeline`. Эта **реальная** регрессия — задача [034](../tasks/034-le-ch01-timeline-preservation.md).

Но! В v36 `chapters[ch_01].timeline` тоже был пуст, и Никите v36 нравится. Значит это **объективная регрессия Stage 3**, но **не та которая объясняет восприятие Никитой различия v36 vs v53b**. Восприятие различия — про вёрстку (53 стр с дублями LD vs 22 стр без дублей).

## Откладываемое решение — переоценка волн 1.1-1.3

Если регрессия #7 (LE deletion) не существовала — стоит ли пересмотреть и предыдущие волны?

- Волна 1.1 (ref-architecture для callouts/historical_notes): закрывала **реальные регрессии #1+#2** — historical_notes 6→0 в PDF (наблюдаемый артефакт через PNG в репо). Это **объективная** проблема, защита нужна.
- Волна 1.2-1.3.x (FC defenses на огурцы): закрывала **реальные** мутации FC которые удаляли эпизод **на Stage 2 итерациях** (v47, v49, v50). Это были **наблюдаемые** регрессии в `book_FINAL_stage2.json`. Защиты сработали — v51 PASS.
- Волна 1.3.3 (GW out-of-scope): закрывала **реальную** регрессию v52 — GW удалил ch_03/ch_04/epilogue. Volume drop 52.8% — наблюдаемый.

**Все предыдущие волны были на реальных классах.** Волна 1.4.0 — первая фантомная.

Что было особенного в 1.4.0:
- v53b — **новый сценарий** (TR2 only, в первый раз)
- Курсор выдал быстрый verdict не дав Опусу артефакт
- Опус принял verdict без независимой проверки

Это **edge case** в процессе, не системная ошибка. Но триггеры выше нужны чтобы он не повторился.
