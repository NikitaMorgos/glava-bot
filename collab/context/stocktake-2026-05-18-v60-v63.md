## 3. Диагноз цикла

### Где мы упираемся

**5 sprints — добавляли правила GW + scripted patterns под каждый новый pattern.** Это работает в коротком плече (конкретный pattern закрыт), но:

1. **GW prompt вырос до ~2 200 строк** (триггер task 037 «refactor ≥2 000 строк» давно сработал).
2. **Validators detect, но не enforce.** Class 12 «Германия+дети» в v63 **flagged как error** в `chronology_check.json`, но в narrative **остался как есть**. Validators висят в воздухе.
3. **Recurring patterns возвращаются в **новых формах**.** Каждая новая форма требует нового pattern в config — это **поверхность**, не корень.
4. **GW cognitive overload на ch_02** (главная глава, max-density правил): v63 ch_02 +38 chars vs v62a (≈ноль роста), хотя ПРАВИЛО 12 явно требовало ≥8K.

### Корневая причина (formulated)

**Текущая архитектура:** GW prompt = единственное место enforcement. Validators = после-факт detector. **Гэп:** detected violations **не возвращаются** GW для исправления.

Аналог: контроль качества на конвейере, который **видит** дефекты, но **не отправляет** деталь на доработку.

### Почему скриптовый подход прекрасен, но недостаточен сам по себе

Скрипты:
- ✅ Detect patterns детерминированно (хорошо)
- ✅ Auto-rewrite для конкретных stop-phrases (волны 043/046)
- ❌ Не могут переписать smysловую регрессию (Class 1 confabulation требует понимания контекста, не regex)
- ❌ Не могут восстановить missing content (Мария missing — скрипт не напишет про неё)

Только LLM (GW) может **переписать смысл**. Поэтому **revision loop** — это «вернуть GW его же выход на доработку с конкретными hints».

## 4. Архитектурный ход v64

**Развилка решена Никитой 2026-05-18:** 1b + 2b + 3c.

### 1b — Revision loop через GW

GW v2.22 → **v2.23 + ПРАВИЛО 13:** «При revision pass — выполнить revision_hints из validators. Получаешь list flagged sentences + reason + suggestion в input → переписываешь только flagged места».

Per Правило 6 — **одно новое правило** (revision compliance), не bundle.

Стоимость: 2 LLM-passes на прогон ($4-6 vs $2-3 раньше).

**Что это закрывает архитектурно:**
- Class 12 «Германия+дети» больше не остаётся в narrative после flag
- Class 1 «определила жизнь» переписывается после flag
- Class 17 «констатация очевидного» удаляется после flag
- Pattern эволюция Class 11 не нужна — validator flag → GW переписывает любую форму

### 2b — Target reformulate

Прежний: Total ≥ 20K (GW gen padding ради цифры).
Новый: **20K = 15K narrative + 3K paspart + 2K historical_notes (objective context)**. Distribution gate, не один chars number.

- Narrative cap 15-17K — реалистичный для 90-минутного интервью без выдумок
- Historical_notes ≥5 inline (восстановить v62a уровень) — скриптовый enrichment из fact_map.timeline + historian agent
- Это **скрипт-first** добивка объёма objective content'ом

### 3c — Class 18 personal-historical voice

Новый класс, не лечился раньше. Реализация:
- **a)** Pin-list секция `narrator_voice_anchors` — examples фраз личного-исторического attribution из TR1/TR2
- **b)** Validator `validate_personal_historical_voice` — детектит patterns

Combined a+b.

## 8. Lessons capture for memory

1. **Validators без enforcement = decorative.** Класс багов «GW игнорирует flag» был **невидим** 5 sprints. Detected только когда Никита прочитал text и сказал «те же замечания что и v62». Lesson: detector работает в гэпе если результат не возвращается в исходный agent.
2. **GW cognitive overload предсказуемо на главной главе.** ch_02 — max density всех правил. Каждое новое GW правило в первую очередь страдает там же. Sign к рефактору промпта (task 037).
3. **Recurring pattern эволюционирует если pattern в config = regex, не семантика.** Class 11 «не любил X по Y и Z» — закрыт snapshot test'ом v62a. v63: «не любил X в принципе, особенно по Y» — обходит regex. Lesson: pattern-based detection всегда behind LLM creativity. Революционный фикс = revision loop с **семантическим** hint, не regex pattern.
4. **Target chars number подталкивает GW к padding.** Никитин feedback v63 явно идентифицировал «нагон объёма». Lesson: gate metric должна измерять **качество**, не количество. Distribution gate (% historical_notes etc.) лучше single number.
