## TL;DR

За 2 недели сделали 9 PR закрывающих 5 классов мутаций (regrессии #1, #2, #3 пять механизмов, #4, GW out-of-scope). Каждая защита спроектирована **общо** (на класс, не на конкретный баг), переведена с промпта на код. Это качественно лучше чем «подорожники».

Но: **все 6 защит это post-condition validators одного типа** — они проверяют что агент не нарушил инвариант. Когда находим новый способ нарушить — добавляем валидатор. Это не системный рефакторинг, а инкрементальная защита по мере появления.

Альтернатива — **constrained interface**: агент структурно не может натворить, потому что выходной формат не позволяет. Самый радикальный кандидат (scripted revision: GW возвращает patches вместо текста) уберёт сразу 2 класса.

Рекомендация: после v53 сделать **минимум один структурный ход** (Кандидат A — запрет `legitimate_deletion` для cross-chapter, ~0.5 дня). Радикальные ходы (B, C) — записать, решать после полного прогона Каракулины.

## Какой системный паттерн за этим стоит

### Все 6 валидаторов защищают **один тип инварианта**

> «Структура и объём контента, переданного агенту, должна быть сохранена при выходе — кроме явно авторизованных агентом изменений».

Конкретно:
- `validate_revision_volume`: объём не уменьшается ниже 95%
- `merge_revision_out_of_scope_chapters`: главы вне scope не меняются
- `validate_layout_fidelity`: элементы layout соответствуют book
- `_verify_evidence_in_book`: удаление имеет подтверждение в источнике
- `enforce_bio_data_completeness`: обязательные поля заполнены

Это **post-condition validators** — они проверяют что агент не нарушил инвариант **после** того как он выдал результат.

### Это говорит о слабости архитектуры агентов

Все наши защиты — реактивные относительно output агента. Агент может «попытаться» что угодно, мы валидируем что он не натворил. Каждый раз когда находим новый способ натворить — добавляем валидатор.

Этому есть имя: **soft contract**. Контракт между нашим кодом и LLM мягкий — output может быть произвольной формы, валидируем семантически.

Альтернатива — **hard contract**: агент структурно не может натворить, потому что **output формат не позволяет**. Например: вместо «GW returns full book.json» → «GW returns list of edits (find/replace/insert) на конкретные chapter+offset». GW структурно не может удалить out-of-scope главу — у него нет такого output формата. Нет нужды в merge_revision_out_of_scope_chapters.

### v52 показал риск этого паттерна

После 5 итераций FC defense (волны 1.2.3 → 1.3.2) мы поймали мутацию **с другого боку** — GW, не FC. Каждая защита покрывает одну дверь, открывается следующая. Whack-a-mole risk.

5 классов мутаций мы закрыли. Но **мы не знаем сколько ещё классов там, потому что не делали структурный аудит выходных контрактов агентов**. Любая новая Stage может открыть новый класс — Stage 3 LE при revision может удалять, Stage 4 LD при auto-patch может терять элементы (это уже было в task 022 про hybrid loop).

## Архитектурные кандидаты (radical)

Перечислены от самого дешёвого к самому дорогому. Стоимость — приблизительная, в днях работы Опуса.

### Кандидат A: Structural alternative для `legitimate_deletion` (cross-chapter)

**Что:** Запретить `legitimate_deletion=true` для cross-chapter ошибок. Любой `framing_distortion` → severity=warning, не major. Не приводит к удалению. Реальный cross-chapter дубль → человек руками решает где оставить.

**Что закрывает:**
- Класс «FC помечает legitimate_deletion для не-дубля» — целиком (мутации v47, v49, v50). Не нужно подкручивать topic_overlap thresholds, shared_tokens мин, object markers test.
- `legitimate_deletion=true` остаётся только для **галлюцинаций** — где FC говорит «эпизод не имеет источника в transcript+fact_map+historical_context», и это легко scripted-проверить.

**Стоимость:** ~0.5 дня. 1 правило в FC v2.13 → v2.14, 1 правило в `validate_revision_volume`, ~5 unit тестов.

**Минус:** теряем automation для **настоящих** cross-chapter дублей. Но они редки в семейных биографиях. Живой человек разрулит.

**Рекомендация:** **Делать после v53, независимо от его исхода.**

### Кандидат B: Scripted revision (hard contract FC → GW)

**Что:** Меняем output FC и input GW при revision.
- FC старый output: `errors[]` с text descriptions + `fix_instruction` (текстовое)
- FC новый output: `errors[]` + `patches[]` со структурой `{type: replace|insert|delete, chapter_id, offset, length, new_text}`
- GW при revision **не пишет заново**, а **применяет patches** через детерминированный код. GW роль сокращается: только creative pass-1/pass-2, не revision.

**Что закрывает:**
- Класс «GW при revision удалил эпизод» — целиком (волна 1.2.2). GW структурно не может, патч либо `replace` либо `insert`.
- Класс «GW out-of-scope при revision» — целиком (волна 1.3.3). Patch привязан к chapter_id, валидатор проверяет.
- Класс «evidence phantom при legitimate_deletion» — частично. FC даёт patch с `delete chapter+offset`, мы проверяем что offset+length реально содержит указанный текст.

**Стоимость:** 5-7 дней. Refactor FC output schema + GW revision pipeline + новый validator + unit + интеграционные тесты + промпт-обновления FC и GW.

**Минус:**
- Серьёзный refactor: FC может потерять nuance (текстовое описание ошибки имеет ценность для куратора).
- Сам по себе может стать источником новых классов (alpha-уровень).
- Не закрывает классы вне revision (Stage 3 LE, Stage 4 LD).

**Рекомендация:** **Записать как кандидат для волны 2.0. Не делать сейчас.** Решать после полного прогона Каракулины (gate2c + gate3 + gate4).

### Кандидат C: FC source-scope как scripted preprocessing

**Что:** Перед FC — детерминированный pre-pass:
- NER на book chapters (русские имена + топонимы + даты)
- N-gram match каждого факта против transcript / fact_map / historical_context
- FC видит preprocessed: «факт X matched в transcript строка Y», «факт Z не matched нигде»
- FC решает только пограничные кейсы (semantic match, парафразы, оценочные суждения)

**Что закрывает:**
- Класс FC bias «адвокат удаления» (наблюдение волны 1.3 отчёта). Когда у FC уже есть baseline по точным совпадениям — он не помечает что-либо как hallucination без причины.
- Снижает FC token cost (input короче — pre-pass отфильтровал явные совпадения).

**Стоимость:** 7-10 дней. NER pipeline для русского биографического текста (можно взять natasha / spacy_russian), n-gram match implementation, FC schema rebuild на pre-passed input, бенчмарки.

**Минус:**
- Сложно. Russian NER — нетривиальный.
- Может ввести новые false positives (NER ошибается чаще чем LLM).

**Рекомендация:** **Записать как кандидат. Не делать сейчас.** Решать после v54+.

### Кандидат D: Holistic скриптование агентов (старый план)

**Что:** 7 агентов из 14 переводим в скрипты. Tier-1 (явно скрипты): Proofreader, QA Layout. Tier-2: Layout Designer + Art Director (частично). Tier-3: Photo Editor.

**Что закрывает:** долгосрочно — снижает соотношение LLM/scripted в пайплайне, делает верификационную часть детерминированной.

**Стоимость:** недели. Каждый агент = отдельная задача-spec → impl → tests → integration.

**Рекомендация:** **После Каракулины.** Сейчас не лезем. task 030 (Proofreader) в `blocked-on-product` — Даша ответит на 3 вопроса, разморозим.

### Кандидат E: Формализовать паттерн post-condition validators

**Что:** Каждому агенту → явный post-validator с инвариантом, который проверяется автоматически в pipeline. Сейчас делаем неявно (validate_revision_volume для GW, validate_layout_fidelity для LD). Формализовать:
```
agent_post_validators = {
  "ghostwriter_revision": [merge_revision_out_of_scope_chapters, validate_revision_volume],
  "layout_designer": [validate_layout_fidelity],
  ...
}
```
Pipeline runner вызывает их автоматически после каждого агента.

**Что закрывает:** устраняет риск что новый агент / новая Stage появится без валидатора.

**Стоимость:** 1-2 дня. Refactor pipeline runner, документировать contract.

**Рекомендация:** **Побочно, в любую следующую волну.** Не отдельная волна.

## Риски моей оценки

**1. Я могу ошибаться о частоте регрессий.** Если v53 = сценарий A — может оказаться что incremental defenses достаточны и B/C никогда не понадобятся. Делать B/C сейчас — over-engineering.

**2. Аудит на который я ссылался — отсутствует.** Это собственный риск кружения: я могу строить рекомендации на отсутствующей базе. Если хотим серьёзно — стоит мне восстановить аудит и положить в репо. Но это +1-2 дня.

**3. Каждый радикальный архитектурный ход (B, C) сам может стать источником регрессий.** «Простой validator» — beta-уровень, 5 регрессий за месяц. «Scripted revision» — alpha, может создать **новые** классы багов. Цена ходов — реальная.

**4. Я могу недооценивать риск whack-a-mole.** В обратную сторону: может оказаться что классов мутаций мало (5-7), мы их быстро закроем incremental, и radical refactors не нужны. Только время покажет.

## Что говорит этот stocktake про процесс

Один честный вывод: **мы реагируем, не планируем.** Каждая волна = реакция на прогон Курсора. Между прогонами — нет stocktake, нет «давайте посмотрим на 5 защит и спросим какой следующий ход даёт максимальную защиту». Этот документ — первый такой stocktake за 2 недели.

Не значит что мы плохо делали — каждая защита нужна и общая. Но значит что **процесс** не самооптимизируется. Если хотим чтобы кружение не вернулось — нужен ритуал stocktake **раз в N волн** (N=3-5), не раз в 2 недели когда я сам предложил.

Это моё предложение для process-памяти команды: после волны 1.4.0 / 1.5.0 сделать второй stocktake. Без триггера от Никиты, по плану.
