# Протокол Dev Review

> Описывает процедуру проверки постановки задачи до начала реализации.
> Введён после серии v29–v32 из-за мискоммуникации между продактом и разработчиком.
> Последнее обновление: апрель 2026.

---

## Зачем

Даша видит задачу со стороны продукта — что должно измениться в поведении.
Cursor видит задачу со стороны кода — как это затрагивает форматы данных, downstream-агентов, стоимость реализации.

Эти два взгляда раньше встречались только в момент реализации. Dev Review — точка, где они встречаются до того как что-то сделано.

---

## Статусный флоу

```
new
  → dev-review       (Cursor прочитал спек, пишет флаги)
  → spec-review      (Claude читает флаги, отвечает)
  → spec-approved    (Даша даёт go — 30 сек скан)
     или
  → blocked-on-product (есть [PRODUCT] флаги без ответа от Даши)
  → in-progress      (Cursor реализует)
  → dasha-review     (Даша проверяет результат)
  → verified-on-run  (фикс прогнан на пилоте с зелёным выхлопом)
  → done
```

**Правила:**

1. Задача не переходит в `in-progress` без `spec-approved`.
2. Задача не переходит в `done` без `verified-on-run` (см. ниже).

---

## Два класса провалов и две защиты от них

Введено 2026-04-30 после разбора Claude Opus, разделено на artifact-провалы и holistic-провалы.

### Artifact-провал

**Симптом:** все промежуточные метрики PASS, но финальный продукт сломан.

**Пример:** регрессия 023. validate_layout_fidelity сказал PASS на 58 абзацев, Cursor отчитал «35 страниц», PDF получил 117KB и exit code 0. Никто не открыл PDF — он содержал 1059 символов вместо 13000+, 92% контента молча отсутствовало.

**Защита:** `verified-on-run` (см. ниже). Открыть финальный артефакт, не верить промежуточным сигналам.

### Holistic-провал

**Симптом:** каждая задача чиста в изоляции, дыры появляются на стыках.

**Пример:** 3 находки Opus после 016/017/018. validate_fidelity вызывался, но результат не использовался. photos_dir guard в одной ветке, но не в симметричной. Auto-patch не учитывал hybrid-элементы. Каждое — корректная реализация спеки своей задачи. Дыра в том что ни одна спека не описывала **взаимодействие** между задачами.

**Защита:** `audit-checkpoint` + регулярный external second opinion (см. ниже). Чтение кода без задачи в голове, поиск противоречий между задачами.

**Не путать.** Это разные ментальные операции. verified-on-run на artifact-провале не поймает holistic-провал и наоборот. Если работать одной защитой — половину времени будешь не в том режиме.

## Защита 1: статус `verified-on-run`

**Правило:** ни одна системная задача (правка кода / промпта / архитектуры) не закрывается как `done`, пока её фикс не прогнан end-to-end и **финальный артефакт не открыт**.

### Posture-forcing требование при закрытии

При переходе из `dasha-review` в `verified-on-run` тот, кто закрывает, **обязан написать одно предложение конкретного наблюдения о финальном артефакте.** Не метрики, не PASS/FAIL, не «файлы на местах» — **что именно видно при открытии**.

**Примеры правильного:**
- «Открыл PDF v38, на стр 5 подглава "Учёба и первая работа" с текстом "В Старобельске Валентина...", всего 17 страниц 14 726 символов»
- «fact_map_v37.json: person_004 Полина Амельченко aliases=['тётя Поля'], без 'Рудая Пелагея Алексеевна' и 'Марфа'»
- «Прогнал normalize с битым layout без --allow-mismatch — получил exit code 1, в stdout три ошибки fidelity»

**Примеры НЕдопустимого:**
- ❌ «validate_fidelity PASS, файлы на местах»
- ❌ «Cursor отчитался об успехе»
- ❌ «Прогон завершён без ошибок, exit code 0»
- ❌ «Статическая верификация Claude пройдена»

**Категория «статическая верификация» из протокола удалена** — это согласие с автором, а не верификация. Если вместо предложения наблюдения о реальном артефакте получается «прочитал диф и согласен» — задача не закрыта, возврат в `in-progress`.

### Что считается «зелёным выхлопом»

- **Для код-задачи:** прогон затронутого этапа пайплайна на пилоте. Финальный артефакт открыт, написано предложение наблюдения.
- **Для алгоритмического фикса** (без LLM): unit-test или repro-скрипт запущен на конкретном входе, выход проверен глазами или сравнением с эталоном.
- **Для промпт-патча:** прогон агента, ответ открыт, проверено что новое правило применено хотя бы раз.

### Кто отвечает

- **Cursor:** после реализации — запустить, приложить артефакты, написать предложение наблюдения.
- **Claude:** не закрывает в `verified-on-run` без предложения наблюдения. Сама пишет своё предложение наблюдения о том же артефакте — если Cursor пишет «PDF на месте», Claude открывает PDF и пишет «вижу 17 страниц, на стр 9 Глава 03». Два независимых наблюдения снижают шанс что оба смотрят не туда.
- **Даша:** financial gate — каждый прогон $2-3, утверждает «гонять или дешевле собрать batch фиксов и прогнать вместе».

### Batch verification

Несколько мелких задач можно верифицировать одним прогоном если их фиксы независимы. В этом случае каждая задача получает своё предложение наблюдения о том же прогоне (разные ракурсы артефакта).

### Почему

Регрессия 023 (2026-04-30): задача 017 закрыта как `done` после фиксов в коде. PDF v37 содержал 1059 символов из 13000+, 92% контента молча отсутствовало. Все промежуточные метрики (35 страниц / 58 абзацев / fidelity PASS / exit code 0) сообщали об успехе. Никто из четырёх (Cursor, Claude, Opus, Даша) не открыл PDF.

Posture-форсинг через предложение наблюдения — лекарство от этого. Если бы любой из четырёх обязан был написать «открыл PDF, на странице X видно Y», то один взгляд сразу бы показал что страниц мало и контент пуст. Задача не закрыта = задача не закрыта.

### Семантическая верификация ≠ формальная (волна 1.2.3, 2026-05-07)

Когда защита возвращает PASS с явным verdict'ом (`ok_with_legitimate_deletion`, `passed_with_override`, и т.п.) — формального PASS **недостаточно**, нужно проверить что **смысл** защиты сохранён.

Третий инцидент того же класса:
- v43 регрессия 23: validate_fidelity вернул PASS на 35 страниц, но PDF был пуст на 92%.
- v45 рефакторинг шаг 2: pytest вернул green, но код не был изменён в файле.
- v47 волна 1.2 верификация (2026-05-07): `validate_revision_volume` вернул `ok_with_legitimate_deletion` потому что FC v2.9 поставил флаг — но FC галлюцинировал основания флага. Эпизод об огурцах исчез из всех глав, защита формально пропустила.

Каждый раз: верный verdict маскировал семантическую дыру.

**Правило:** для каждого PASS-verdict'а с условиями (`ok_with_X`, `passed_with_Y`) — обязателен **cross-check на смысл условия**. PASS — это что код пропустил по правилам; семантика проверяется отдельно:

| Защита | Формальный PASS | Семантический cross-check |
|---|---|---|
| validate_layout_fidelity | количество ref'ов совпадает | открыть PDF, проверить что текст реально рендерится |
| validate_revision_volume `ok_with_legitimate_deletion` | FC поставил флаг | проверить что evidence quote реально есть в book_after (волна 1.2.3) |
| validate_revision_volume `ok_within_threshold` | объём ≥ 95% | проверить что важные эпизоды сохранены (по pin-list если есть) |
| pytest passes после refactor | все тесты green | прочитать diff в файле — реально ли структура изменилась |

В коде это означает: каждая проверка с `passed_with_*` verdict'ом требует доп. проверку которая проваливается если условие фейковое. В процессе это означает: при verdict'е с условием обязательно записать «верифицировал условие через X» в observation sentence.

## Защита 2: `audit-checkpoint` (holistic-режим)

**Правило:** периодический systemic review кода без привязки к конкретной задаче.

### Триггеры (структурные, не календарные)

Аудит обязателен когда сработал любой:

1. **Кластер 2+ задач трогает один subsystem.** Пример: 016/017/018 — все про Stage 4. Каждая чистая в изоляции, дыры на стыках появились в кластере.
2. **Контракт между компонентами меняется.** Пример: после 017 формат layout.json новый — все его читатели должны быть пересмотрены, не только Layout Designer.
3. **В описании задачи слова «orchestration» / «обвязка» / «protocol».** По определению означают межфайловые взаимодействия которые в одном файле не видны.
4. **Задача планирует закрываться только статической проверкой кода.** Это запах. Не валидация — запах.
5. **Календарный backup:** прошло > 3 недель без holistic-прохода → независимо от структурных триггеров, аудит. Страховка от случая когда триггеры пропустили.

### Дисциплина прохождения

1. **Открывать код слепо, БЕЗ спеки задачи.** Сначала чтение, потом сверка с ожиданиями. Если порядок обратный — ищется подтверждение априорных ожиданий, а не противоречия.
2. **Вопрос на проходе:** «Что меня здесь удивило?» — не «Соответствует ли спеке?»
3. **Искать на стыках.** Где результат вызова не используется. Где guard есть в одной ветке но не в симметричной. Где формат на выходе одного компонента не учитывается на входе другого.
4. **Список наблюдений → новые задачи или комментарии в существующие.** Audit-проход не правит код, а размечает проблемы для отдельных задач.

### Кто и когда

- **Claude (я):** провожу аудит при срабатывании структурных триггеров. По оценке Opus — закрываю ~70% holistic-провалов сама.
- **External second opinion** (Opus или другая модель): **раз в 3-4 системные задачи** — независимый проход «слепо посмотри». Это не часть основного процесса, а **контр-якорь от блайнд-спота «не вижу чего нет»**. Дешевле и надёжнее чем растить self-audit-дисциплину до уровня поиска отсутствующих вещей.

### Почему 70/30

Self-audit структурно не закрывает блайнд-спот «не видишь чего нет». Если в моём контексте есть объяснение почему `validate_fidelity` вызывается — я не задам вопрос «а используется ли результат», потому что объяснение это скрывает. Внешняя модель без этого контекста спросит первой. Это не вопрос внимательности, это структурное ограничение позиции автора.

### Почему

Разбор Opus 2026-04-30 показал что наши 4 актора (Cursor, Claude, Opus до этого, Даша) работали в режиме incremental delivery. Каждая спека узкая, каждое ревью узкое. Holistic-режим (читать код без задачи, искать противоречия) ни в чьей роли не было. Opus за 30 минут нашёл 3 критичных бага которые мы делали 3 итерации.

## Классификация флагов

### [TECH] — технические флаги

Cursor поднимает, Claude отвечает автономно.

Примеры:
- изменение формата данных (ломает downstream-агента)
- side effect на другой стейдж пайплайна
- существует более простая альтернатива реализации
- спек неполный: не описан edge case или поведение при ошибке
- temperature / max_tokens противоречат текущим стандартам

### [PRODUCT] — продуктовые флаги

Cursor поднимает, **обязательно отвечает Даша** (не только Claude).

Примеры:
- неясно какой UX-результат считается успехом
- спек противоречит предыдущему решению по продукту
- критерий приёмки в спеке отсутствует или субъективен
- затрагивается политика (оплата, данные пользователей, роли)

---

## Лимит итераций

**1 раунд** — Cursor пишет флаги, Claude/Даша отвечают.

Если после одного обмена не сошлись → статус `blocked-on-product` → эскалация к живым людям.

Это защита от «вежливого согласия между AI» — когда модель соглашается чтобы закрыть тему, а не потому что проблема реально решена.

---

## Финальный sign-off

Даже если Dev Review прошёл быстро и без разногласий — **Даша явно даёт go**.

Это не бюрократия, а точка ответственности: после `spec-approved` Cursor начинает реализацию, и откат дороже.

Формат sign-off: Даша меняет статус задачи на `spec-approved` в файле задачи (или пишет "go" в Dev Review Response).

## Артефакт, не побочный эффект

**Правило верификации:** при проверке любого «X сделано» — открой сам артефакт изменения, а не его proxy-метрики.

**Что НЕ является верификацией:**
- Отчёт исполнителя «всё сделано, всё green» (в т.ч. от другой модели — Cursor / Claude / Codex). Это гипотеза, не факт.
- `pytest passes` после рефакторинга кода — тесты могут пройти на неизменённом коде, если сам refactor не записан в файл.
- `subprocess.run(...).returncode == 0` после сборки артефакта — exit code 0 не означает что артефакт содержит то, что должно (PDF может собраться пустым, JSON может быть синтаксически валидным но семантически кривым).
- «Файлы на местах», «структура корректна», «manifest зелёный» — статусы об одних slots, не о другом.

**Что является верификацией:**
- Открыть результирующий файл / артефакт / диф напрямую и прочитать содержимое.
- Если артефакт PDF — извлечь текст и сравнить с источником.
- Если артефакт код — прочитать diff, не только статус «закоммитил».
- Если артефакт изменение конфига / промпта — открыть файл и убедиться что нужная строка действительно записана.

**Почему это правило существует:**
Зафиксировано после двух подряд инцидентов:
1. Регрессия 23 (v43 PDF теряет 92% контента). Cursor отчитал по `subprocess exit code == 0` и `validate_fidelity PASS`. Никто не открыл финальный PDF — все proxy-метрики были зелёные.
2. Рефакторинг validate_fidelity (волна 1.1, шаг 2). Cursor отчитал «`REF_TYPE_CONFIG` добавлен, тесты green». В реальности — файл `scripts/validate_layout_fidelity.py` не был изменён. Тесты при этом действительно проходили — потому что они проверяют поведение, а текущее поведение работало (refactor не сделан, behavior preserved тривиально).

В обоих случаях сбой одного класса: **статус «сделано» закрывался по форме отчёта, не по факту записи в артефакт**.

Это правило применяется и к Dev Review (Cursor читает код, не описания изменений), и к dasha-review (Claude/Даша читает diff и сам файл, не «green по тестам»), и к verified-on-run (открыть конечный артефакт глазами или скриптом, проверить содержимое).

## Что Cursor проверяет при Dev Review

Обязательный чеклист при заполнении секции Dev Review:

- [ ] Все выходные форматы задачи совпадают с тем что ожидает следующий агент
- [ ] Нет неявного изменения формата `book_draft.json`, `fact_map.json`, `layout.json`
- [ ] Если меняется промпт — указан агент, версия и температура
- [ ] Если меняется код — описан затронутый модуль и тип изменения
- [ ] Критерий приёмки ("как проверить") конкретный и верифицируемый
- [ ] Спек не противоречит `pipeline-run-protocol.md`

---

## Исключения

Dev Review **не обязателен** для:
- задач типа `промпт` без изменения формата данных (минорная правка стиля, тона, примеров)
- задач со статусом `hotfix` (срочное исправление поломки в продакшне)

В этих случаях в поле Dev Review пишется: `skipped — [причина]`.

## Архитекторская дисциплина (введено 2026-05-08, Этап 1 рефакторинга)

Роль архитектора в команде формально принадлежит Опусу. После серии 9 PR волн (1.1-1.3.3) и одной фантомной волны 1.4.0 (PR #14, отменён) выяснилось что архитектор не исполнял свою роль системно — выпадал в tactical patcher. Введены 3 правила для возврата к архитекторской функции.

### Правило 1 — План перед волной

> Любое предложение «давай делать X» из Опуса должно начинаться **с плана**, не с кода. План включает: цель, реперные точки, definition of done, что НЕ делаем.
> Если плана нет — Никита/Даша вправе сказать «дай план», и Опус обязан остановиться. Кодовая реализация — только после согласованного плана.

### Правило 2 — Артефакт перед проектированием

> Никогда не проектирую защиту до **личного открытия артефакта** в репо.
> Курсорский пересказ «X не работает» — это **proxy**, не факт. Опус обязан открыть `book_FINAL`, `liteditor_report`, PDF или соответствующий артефакт перед написанием защиты.
> Артефакт в чате как «вот тут видно...» — недостаточно. Нужен файл в репо (или прямое чтение через `git show <branch>:<file>`).
> Прецедент: PR #14 (волна 1.4.0). Спроектирована защита от «LE удалил огурцы» на основе Курсорского пересказа. При прямой проверке артефакта — огурцы в `book_FINAL_stage3_v53b.json` присутствуют. Защита фантомная. Время потеряно.

### Правило 3 — Stocktake каждые 2-3 волны (УСИЛЕНО 2026-05-19 после v63 промаха)

> **Жёсткий триггер счётчика прогонов:** после каждого **3-го verified-on-run** Опус **обязан сделать stocktake-документ ДО проектирования следующего sprint**. Без stocktake — sprint plan v_(N+1) не пишется, спецификации не commit'ятся.
>
> Stocktake — короткий документ (1-3 страницы): что закрыли (закрыто навсегда vs recurring vs новые классы), есть ли цикл diminishing returns, какой архитектурный ход даёт максимальный impact, какой план НЕ делаем (явный exclude list).
>
> **Процедура (включена в pre-sprint checklist в `_template.md`):**
> 1. Счётчик verified-on-run прогонов с прошлого stocktake — если ≥3, stocktake обязателен
> 2. Critical reading артефактов последнего прогона (открыть text_FULL.md, прочитать narrative главами, искать новые классы багов)
> 3. Создать `stocktake-YYYY-MM-DD-v_X-v_Y.md` в `collab/context/`
> 4. В sprint plan для v_(N+1) — ссылка на свежий stocktake в шапке
> 5. Если ≥3 прогонов прошло без stocktake — **остановиться**, сделать stocktake, потом sprint
>

### Правило 6 — Prompt engineering дисциплина (введено 2026-05-17 после v60)

> **При расширении GW (или любого LLM-агента) — 1 новое правило per prompt-bump.** Не bundle 2+ новых правил в один промпт.
>
> Между правками **обязательный прогон verify** — проверить что старые правила не деteriorировали.
>
> **Альтернатива (предпочтительно по Правилу скрипт-first):** новые features = **скрипты**, не промпт-extensions. Когда возможно реализовать через post-process — выбирать скрипт. Промпт-extension только когда алгоритмически невозможно (generation discourse markers, стиля narrative).
>
> **Почему:**
> - LLM имеет ограниченный attention. При балансировке 10+ правил каждое новое добавляется в ущерб качеству предыдущих.
> - «Cognitive overhead» — LLM фокусируется на новых правилах за счёт деталей старых.
> - Скрипт = детерминированное правило, не балансируется с другими.
>
> **Прецедент v60 sprint (2026-05-17):**
> - GW v2.20 (v59) — баланс правил 1-8 + ЗАПРЕТЫ 12-15, narrative quality высокая
> - GW v2.21 = v2.20 + **3 новых ПРАВИЛА** одним bump (9 temporal place names + 10 contributors + 11 chapter sections anchors)
> - v60 регрессировал 5+ деталей контента — GW v2.21 «забыл» Власьево / разные отцы / Маня / French бабушка / детский сад
> - **Stage 1 (CA v1.4) данные сохранил** — все persons + events в fact_map v60. GW не использовал.
> - Diagnostic: классический pattern overload в LLM. 3 правила за раз = слишком.
>
> **Как теперь:**
> 1. Каждое новое ПРАВИЛО в GW = **отдельный промпт-bump** (GW v2.X+1)
> 2. Между bumps — прогон verify (~$2-3 на каракулиной, дешёво)
> 3. Если v_N после правила X показывает regression на старых деталях — **откатить** правило X, реализовать через скрипт
> 4. **Никогда** bundle 2+ правил в один prompt-bump
>
> **Для новых features (когда продакт просит):**
> 1. Сначала ask: реализуемо ли скриптом? (post-process, validation, enforce)
> 2. Если да → скрипт (Класс defense)
> 3. Если нет → промпт, **по одному правилу за раз**

### Правило 7 — Не экономим на тестовых прогонах (введено 2026-05-19 после v63 промаха)

> **На этапе борьбы за стабильное качество — каждый sprint, требующий verify, идёт отдельным прогоном.** Не объединяем 2+ независимые изменения в один прогон ради экономии $2-3.
>
> **Причина:** диагностика дороже экономии. Если 10 scripted + 1 GW prompt + 1 CA patch в одном прогоне дают плохой результат — невозможно сказать что именно сломало (что улучшило, что регрессировало). Прогон вслепую = $2-3 потрачены без diagnostic ценности.
>
> **Когда нарушать:** только когда **все** изменения — узкие bugfixes реализации (не новые features, не новые правила, не риски регрессии). Combined OK для исправления багов с известным эффектом, не для добавления новых mechanisms.
>
> **Когда соблюдать строго:**
> - GW prompt-bump (новое правило) — **отдельный прогон**
> - CA prompt-bump (новое правило) — **отдельный прогон**
> - Архитектурное изменение (revision loop, новый agent) — **отдельный прогон**
> - Pin-list major restructuring — **отдельный прогон**
>
> **Когда не соблюдать (combined sprint OK):**
> - Несколько узких bugfixes одного класса (например 5 patch'ей в `narrative_stop_phrases.json` все scripted)
> - Hot-fix предыдущего sprint'а с понятными причинами
>
> **Принцип Никиты (зафиксировано 2026-05-19):** «сейчас нам важней результат стабильный получить. экономить можно начать позже».
>
> **Прецедент v63 (combined Опция X):** 10 scripted + 1 GW rule + 1 CA rule + pin-list update + 5 configs в одном прогоне ($2-3). Результат: 11/11 task PASS code-side, но **невозможно** диагностировать что именно дало регрессию объёма (ch_02 +38 chars). Сэкономили $2-3, потеряли диагностику. v64 = архитектурный ход который надо было сделать в v63 если бы делали split.

### Правило 8 — Класс багов лечится семантикой, не regex (введено 2026-05-19 после v60-v64 цикла)

> **Регулярка (`narrative_stop_phrases.json` pattern) — это детектор конкретной формы, не лечение класса.** Class лечится только семантически — через LLM с пониманием смысла.
>
> **Почему:**
> - Regex покрывает конкретные сочетания слов (синтаксис)
> - Класс определяется по смыслу (семантика)
> - GW каждый раз пишет немного иначе — новые формы пробивают старые regex
> - Каждый sprint мы добавляли паттерны под новую форму — это бесконечная гонка
>
> **Прецеденты эволюции pattern'ов:**
> - Class 11 «X-по-Y listing»:
>   - v62a: «не любил советов **по электричеству и поездкам**» — regex match
>   - v63: «не любил советов **в принципе, особенно по практическим вопросам — будь то электричество или распорядок поездок**» — regex обходит
>   - v64: «не любил советов — **особенно по электричеству, поездкам и другим бытовым вопросам**» — regex обходит снова
> - Class 1 «causal confabulation»:
>   - v62a: «огурцы — критиковала за подарки **из командировок**» (location generalisation)
>   - v63: «**ей казалось, что родственники мужа должны присылать больше подарков**» (motivation confabulation)
>   - v64: продолжение в новых формах
>
> **Архитектурный принцип проектирования валидатора:**
>
> 1. **Сначала спросить:** возможен ли семантический detector (LLM-based, structural rule типа year vs birth_year, similarity check к источнику)?
>    - Если да — реализовать через семантику. Лечение = понимание смысла.
>
> 2. **Если только regex возможен:**
>    - Считать его **минимальным detector'ом** (поймать last known form)
>    - **Обязательно** подключить к поправляющему проходу с **семантическим hint** (`suggestion` поле в revision_hint): «удалить причинно-следственную связку которой нет в источнике», не «удалить sentence matching regex X»
>    - GW при revision получает смысл + 1-2 примера → ловит вариации
>    - Snapshot test для каждой найденной формы (минимум, чтобы старая форма не возвращалась)
>
> 3. **Лечение класса = смысловой suggestion в revision_hint**, не regex pattern. Regex — backup для detect, не для fix.
>
> **Прецедент v64:** revision loop через ПРАВИЛО 13 GW начал переписывать flagged sentences по smyslовому hint. Это **первый случай** когда defense работает на уровне семантики, не на уровне regex. Архитектурно правильно. Реализация partial (orchestrator bugs — task 049f-2 в v65), но направление верное.

> - **Diagnostic:** при регрессии быстро локализовать «какая версия изменилась между runs N и N+1»
> - **Verification:** PASS verdict без зафиксированных версий — это PASS «чего-то», не воспроизводимый артефакт
>
> **Прецедент:** До 2026-05-17 registry не велся. Восстановлено ретроспективно для v54-v59 (после Никитиного вопроса «ведёшь ли четкий реестр?»). Признан пробел в дисциплине архитектора с момента отстранения Даши/Клода.

### Правило 6 — Prompt engineering дисциплина (введено 2026-05-17 после v60)

> **При расширении GW (или любого LLM-агента) — 1 новое правило per prompt-bump.** Не bundle 2+ новых правил в один промпт.
>
> Между правками **обязательный прогон verify** — проверить что старые правила не деteriorировали.
>
> **Альтернатива (предпочтительно по Правилу скрипт-first):** новые features = **скрипты**, не промпт-extensions. Когда возможно реализовать через post-process — выбирать скрипт. Промпт-extension только когда алгоритмически невозможно (generation discourse markers, стиля narrative).
>
> **Почему:**
> - LLM имеет ограниченный attention. При балансировке 10+ правил каждое новое добавляется в ущерб качеству предыдущих.
> - «Cognitive overhead» — LLM фокусируется на новых правилах за счёт деталей старых.
> - Скрипт = детерминированное правило, не балансируется с другими.
>
> **Прецедент v60 sprint (2026-05-17):**
> - GW v2.20 (v59) — баланс правил 1-8 + ЗАПРЕТЫ 12-15, narrative quality высокая
> - GW v2.21 = v2.20 + **3 новых ПРАВИЛА** одним bump (9 temporal place names + 10 contributors + 11 chapter sections anchors)
> - v60 регрессировал 5+ деталей контента — GW v2.21 «забыл» Власьево / разные отцы / Маня / French бабушка / детский сад
> - **Stage 1 (CA v1.4) данные сохранил** — все persons + events в fact_map v60. GW не использовал.
> - Diagnostic: классический pattern overload в LLM. 3 правила за раз = слишком.
>
> **Как теперь:**
> 1. Каждое новое ПРАВИЛО в GW = **отдельный промпт-bump** (GW v2.X+1)
> 2. Между bumps — прогон verify (~$2-3 на каракулиной, дешёво)
> 3. Если v_N после правила X показывает regression на старых деталях — **откатить** правило X, реализовать через скрипт
> 4. **Никогда** bundle 2+ правил в один prompt-bump
>
> **Для новых features (когда продакт просит):**
> 1. Сначала ask: реализуемо ли скриптом? (post-process, validation, enforce)
> 2. Если да → скрипт (Класс defense)
> 3. Если нет → промпт, **по одному правилу за раз**

## Триггеры отката (введено 2026-05-08, стратегия реперных точек)

Стратегия рефакторинга использует **реперные точки (RP-0 → RP-6)** — git-теги + checkpoint-документы. На любой точке можно откатиться если последующий этап создал проблему.

### Сильные триггеры (откат обязателен)

1. **Регрессия в работающей области.** На прогоне найдена регрессия в функциональности которая работала на предыдущей RP. Например: после RP-3 огурцы снова теряются, хотя на RP-2 они были. Откат на ближайшую RP где это работало.

2. **>3 регрессий разных классов** на одном прогоне. Это сигнал что предыдущий этап неудачен. Ретро + откат на предыдущую RP.

3. **Дашин чек-лист провален** в большей части пунктов чем на предыдущей RP. Деградация продукта по основной метрике.

### Слабые триггеры (обсуждение, может быть откат)

4. **>2 новых классов багов** между текущей точкой и предыдущей RP. Решаем «продолжить fixing или откатиться и пересобрать».

5. **Курсор/Опус не понимают что сломалось.** Это уже само по себе сигнал неустойчивости.

### Кто принимает решение об откате

**Никита.** Опус / Даша / Курсор могут предложить — go даёт Никита. Откат — destructive операция (`git reset --hard <RP-tag>`), теряет работу после tag. Безопаснее: создать новую ветку от tag, продолжить с этой точки (`git checkout -b restart-from-rp-N <RP-tag>`).
